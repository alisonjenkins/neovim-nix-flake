# Stream viewer: motions and commands audit

Generated by `tests/nvim/streammotions_doc.lua` from `tests/nvim/streammotions_rows.lua` and a run of the
`streammotions-*` flake checks. Do not edit the tables by hand: change the rows, rerun the checks, regenerate.

The viewer shows a window of lines of a file that does not fit in memory. A user of such a file (multi-GB
logs, YAML, minified JSON on ONE line) types the same commands as in any file and expects Vim's result. Each
row below is a class of commands, what Vim does, what the viewer does today (measured against the build this
was generated from), whether it belongs in the viewer, and the test that pins it.

## Reading the table

- **Rank**: how likely a heavy log/JSON/YAML user types it. 1 = daily, 5 = rare. Implementers: do rank 1 and 2 first.
- **Applies**: `many` = a huge file of many lines, `one` = a huge single line, `both`.
- **Today**: `ok`, `partial (pass/total cases)`, `unsupported` (every case fails), `wrong` (a probe fails). Rows with a
  single-line variant show both (`one line:`); the test id of that variant ends in `@1`; scale tests end in `@big` for 2 GB / 1 GB.
- **Scope**: `yes`; `limits: ...` (in scope with a stated limit); `no: ...` (out of scope, with the reason).
- **Test id**: the key in `tests/nvim/streammotions_status.lua` (`pass`, `xfail`, `skip`). Flip an id to `pass` when you fix it.

## How the tests work

- Differential rows (`chk` nav, txt, edit, search): the same keys run in a stock Neovim (`--clean`, the file loaded
  whole) and in the viewer, in two child Neovims, from the same absolute byte offset, on files of a few MB. The viewer's
  `block`, `slice`, `head` and `window_budget` are set to 1-256 KB (the defaults are 256 KB, 2 MB, 64 KB and 16 MB) so that every motion crosses block edges and the slice of a 1 MB line slides. Compared: absolute byte
  offset of the cursor, mode, visual anchor, registers, marks, and for edits the whole resulting text (sha256).
  Sequences are curated per row plus seeded random ones (`STREAM_SEED`, `STREAM_CASES` percent); a failure prints the
  shrunk key sequence, file, start offset, configuration and seed.
- Probes (`misc`, `scale`): hand-written checks of save/quit states, takeover, cancel, folds, display and the time and
  peak memory budgets on planted 64 MB (and, in `streammotions-scale-huge`, 2 GB / 1 GB sparse) files.
- Seams the tests use that the viewer keeps: `require('streamview').cursor_offset(S)` (absolute cursor byte),
  `.place(S, byte)` (cursor to an absolute byte, waits for the scan), `S.job` non-nil while a scan or save runs,
  `.render`, `.state`, `S.r:get`, `S.r.size`; `streamnav.lua` pins the first two. A visual anchor or a mark is read from
  the rows (`S.entries[lnum].from` + the byte column).

## Decisions

- `:g`, `:s` and ex ranges on huge files: in scope as streaming passes for `d y s normal t w`; a command that cannot stream is refused with a message, never applied to the window only (`%` means the whole file).
- Splits of the viewer buffer: allowed, both windows show the same slice (`win.split`). Independent views: out of scope.
- Folds: forced off (`fld.off`). Line numbers: not shown, the winbar shows the byte offset (`x.number`, `x.fileinfo`).
- `{N}%` is a byte percentage within 1 percent of Vim's line percentage (`jmp.pct`).
- Insert-mode completion is off (`ins.completion`). Filters (`:%!cmd`) are out of scope.
- A scan that can take long (search, `%`, `}` over GBs) runs in slices, shows progress, is cancelled with `<C-c>`, keeps memory bounded and never blocks the editor (`can.*`, `scale.*`).
